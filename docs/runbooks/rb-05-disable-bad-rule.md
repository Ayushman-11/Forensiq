# RB-05 — Disable a Bad Detection Rule

**Severity:** P2 — alert storm / analyst overload  
**Owner:** Platform on-call  

---

## When to use this runbook

- A detection rule is producing a high volume of false-positive alerts.
- `forensiq_ingest_alerts_new_total` spikes sharply on a single `rule_name`.
- Analysts report an unworkable backlog from one rule.

---

## How rules work today

Detection rules live in `backend/app/services/detection_rules.py` as Python functions.  
The noise-suppression policy lives in `backend/config/noise.yaml`.

There are two ways to disable a rule:

| Method | Effect | Requires deploy? |
|---|---|---|
| Noise policy (YAML) | Events matching the suppression criteria are dropped before rule evaluation | No – hot-reload on next cycle |
| Comment out the rule in Python | Rule never runs at all | Yes – code change + deploy |

**Prefer the noise policy** for immediate suppression while you investigate.  
Use the code change for a permanent fix.

---

## Option A — Suppress via noise policy (immediate, no deploy)

### Step 1 — Identify the noisy rule

```bash
# Check which rule is firing most in the last hour
mongosh "$MONGO_URI" --eval "
  db = db.getSiblingDB('forensiq');
  db.alerts.aggregate([
    { \$match: { created_at: { \$gte: new Date(Date.now() - 3600000) } } },
    { \$group: { _id: '\$rule_name', count: { \$sum: 1 } } },
    { \$sort: { count: -1 } },
    { \$limit: 10 }
  ]).forEach(printjson);
"
```

### Step 2 — Add a suppression entry to `config/noise.yaml`

Open `backend/config/noise.yaml` and add a rule-level suppression:

```yaml
rules:
  - name: suppress_dns_suspicious_query_global   # or any name
    conditions:
      rule_name: dns_suspicious_query             # exact rule_name to suppress
    reason: "RB-05: suppressed YYYY-MM-DD, tracking ticket #XYZ"
```

Or suppress by a specific source:

```yaml
rules:
  - name: suppress_dns_github_lookup
    conditions:
      rule_name: dns_suspicious_query
      dest_domain: github.com
    reason: "RB-05: GitHub DNS lookups are legitimate"
```

### Step 3 — Reload the noise policy

The noise policy is loaded from disk on each ingestion cycle (not cached across cycles).  
**No restart is needed** — the next cycle will pick up the new suppression.

Verify by watching the suppressed counter:

```bash
watch -n 5 'curl -s http://localhost:8000/metrics | grep forensiq_ingest_suppressed_total'
```

## Option B — Disable the rule in code (permanent)

### Step 1 — Locate the rule

```bash
grep -n "dns_suspicious_query\|rule_name" backend/app/services/detection_rules.py | head -20
```

### Step 2 — Comment out or delete the rule function

```python
# DISABLED: RB-05, YYYY-MM-DD, ticket #XYZ — high false-positive rate
# def dns_suspicious_query_rule(fields: dict) -> bool:
#     ...
```

Or set `match_fn = None` on the rule object so it is registered but never fires:

```python
DetectionRule(
    name="dns_suspicious_query",
    # match_fn=_dns_suspicious_query,  # disabled: RB-05
    match_fn=None,
    ...
)
```

### Step 3 — Deploy

```bash
git add backend/app/services/detection_rules.py
git commit -m "chore: disable dns_suspicious_query rule (RB-05, ticket #XYZ)"
git push origin main
# CI will build and deploy
```

---

## After the storm is over

1. Review the alerts generated by the bad rule. Bulk-close false positives via the dashboard.
2. Tune the rule's logic or suppression conditions so it has acceptable precision.
3. Re-enable via a code change or by removing the noise policy entry.
4. Document precision metrics before and after in the deployment changelog.
